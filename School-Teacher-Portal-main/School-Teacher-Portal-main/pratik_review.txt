Teacher Portal — Detailed Review & Required Further Development
I reviewed the current School Teacher Portal implementation against the provided School Enterprise Platform – Daily Academic Operations & Teacher Experience, Stage 1 requirements. The Stage 1 scope is intended to cover the teacher's complete academic operating workflow, including assigned classes and subjects, attendance, examinations, marks, assignments, dashboards, and academic performance.
The current implementation provides a basic foundation, but it should not yet be considered complete Stage 1 implementation. The portal currently demonstrates the main dashboard, classes, assignments, and exams/marks areas, but several required workflows and detailed teacher workspaces are still missing or need substantial expansion.
Please use the following as the development review and required next-work specification.
1. Rework the Information Architecture
The current primary navigation is too limited:
Dashboard → My Classes → Assignments → Exams & Marks
The teacher needs a clearer academic workspace.
A recommended structure is:
DashboardMy ClassesMy SubjectsAttendanceAssignmentsExams & MarksReports
However, do not create unnecessary standalone pages when a feature logically belongs inside a Class, Subject, Student, Assignment, or Assessment workspace.
The principle should be:
Global navigation tells the teacher where they are working. Contextual actions inside each workspace tell the teacher what they can do.
The Stage 1 specification explicitly requires screens including My Subjects, Class Student List, Student Academic View, Attendance Entry, Attendance History, Attendance Correction Request, Exam List, Marks Entry, Marks Submission, Assignment Details, Submission/Feedback View, Subject Performance, and Class Performance.

3. Properly Support Class Teacher vs Subject Teacher
This is one of the most important areas to implement correctly.
The system must distinguish between:
Subject Teacher
A subject teacher operates within:
Assigned Subject + Assigned Classes/Sections
Class Teacher
A class teacher additionally has an overall operational view of the assigned class.
Teacher With Both Roles
A teacher who is both should receive the union of their explicitly assigned scopes, not unrestricted access.
This is consistent with the Stage 1 access rules.
Class Teacher — All Subjects View
For example, if a teacher teaches Mathematics and is also the Class Teacher for Grade 10-A, opening Grade 10-A should allow them to see the class's subjects:
Mathematics
English
Physics
Chemistry
Biology
Social Science
etc.
For each subject, show appropriate information such as:
Subject teacher
Recent assessment
Class average

Pending academic activity
But:
Viewing another subject must not automatically grant editing rights for that subject.
For example:
Mathematics→ View + permitted academic editing
Physics→ Class-level overview/read access unless the teacher is separately assigned/authorized for Physics
A Mathematics teacher must not be able to edit Physics marks simply because they are the class teacher.
The authorization model must therefore drive both the UI and backend/API permissions.

12. Professional UI/UX Revision
The current interface has a clean foundation, but it should be refined to feel like a professional school operations product, rather than a basic dashboard/demo.
Do not redesign everything unnecessarily. Improve the existing design system and information hierarchy.
Reduce Oversized Components
Cards and buttons currently consume more space than necessary.
Actions such as:
Attendance
Review Pending
Enter Marks
do not always need to occupy almost the entire card width.
Use clear action hierarchy:
Primary Action → Filled brand buttonSecondary Action → Outline/neutral buttonNavigation/Details → Text/icon action
Reduce Excessive Whitespace
Desktop/tablet layouts should use available screen width more effectively.
Avoid stacking everything into oversized single-column cards when the information can naturally be displayed in a two-column layout.
Use:
Summary cards for KPIs
Tables for dense operational data
Lists for repetitive records
Cards for meaningful grouped information
Reduce Excessive Rounded Styling
The current design uses very large rounded corners across almost every component.
Move toward a more restrained professional design language:
Cards → moderate radius
Buttons → moderate radius
Inputs → moderate radius
Status chips → pill shape
The interface should feel polished rather than overly playful.
Improve Typography Hierarchy
Establish consistent levels for:
Page title
Section heading
Card title
Body text
Metadata
Caption
Important information should have stronger visual priority than secondary metadata.
Establish Consistent Semantic Colors
Maintain the existing brand/accent direction but use colors consistently:
Green → Completed / Published / HealthyAmber → Pending / AttentionRed → Overdue / Error / AbsentTeal/Brand Color → Primary action / InformationGrey → Inactive / Closed / Draft
Avoid excessive use of bright colors.

15. Permissions Must Drive Both UI and Backend
Do not solve authorization simply by hiding buttons.
The Stage 1 access model is:
Class Teacher→ Assigned class academic/attendance scope
Subject Teacher→ Assigned subject + assigned classes/sections
Teacher with Both Roles→ Union of explicitly assigned scopes
Unauthorized Teacher→ No access to unrelated classes, students, or subjects.
The backend/API must enforce the same rules.
For example:
A Mathematics teacher must not be able to modify Physics marks by manually changing an ID in a request.
The Stage 1 acceptance criteria explicitly require backend authorization testing for cross-class and cross-subject access.
Therefore test:
Cross-class access
Cross-subject access
Unauthorized student access
Unauthorized marks modification
Unauthorized attendance modification
Unauthorized assignment creation
Unauthorized assessment access
16. Connect the Workflows Properly
The portal should not feel like a collection of isolated screens.
The expected navigation should feel like:
Dashboard → Today's Class → Class Workspace → Student → Student Profile
My Classes → Class → Attendance → Submit → Attendance History → Correction
My Classes → Class → Students → Student Academic Profile
My Subjects → Mathematics → Grade 10-A → Performance
Assignments → Assignment → Submissions → Student → Feedback
Exams & Marks → Assessment → Marks Entry → Draft → Submit → Published
Class Teacher → Class → Subjects → Subject Summary → Students / Performance
Every screen should provide logical next actions.
The user should never have to return to the dashboard simply to continue a workflow that could naturally continue from the current screen.

Maintenance/repair

19. Follow the Existing Data/API Boundaries
Student, class, section, subject, and teacher-assignment information should be consumed from the agreed foundation APIs.
Do not:
Duplicate student master records
Create another user/role system
Directly modify another package's tables where an API exists
Bypass established APIs
The Stage 1 document specifically establishes these integration and independence rules.

Expected Final Outcome
The final Teacher Portal should not feel like four separate dashboard pages.
It should feel like a single, connected Teacher Academic Operations Workspace where a teacher can perform their complete daily work:
See what needs attention → open the relevant class/subject → work with students → take attendance → manage assignments → conduct assessments → enter/submit marks → review performance → handle permitted corrections and remarks.
The priority is functional completeness + clear workflows + correct role permissions + professional UI/UX + responsive design.
Please treat the existing implementation as a foundation and complete/refine it rather than simply adding more static screens.
