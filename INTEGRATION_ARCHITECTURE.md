# School Enterprise Portal Integration Architecture

## Decision

Deliver one School Management platform through two role-specific frontends and one shared Spring Boot backend:

```text
Administrator React/JavaScript SPA ─┐
                                    ├── shared HTTP API ── Spring Boot modules ── MySQL
Teacher React/TypeScript SPA ────────┘                    └── Flyway schema history
```

The frontends are separate presentation clients, not separate school systems. The shared backend owns authentication, authorization, identity, validation, and all domain/business rules. Both applications use the same backend origin and common domain records while presenting only their role-appropriate workflows.

## Component decisions

| Component | Decision | Rationale and boundary |
|---|---|---|
| Administrator frontend | Keep `frontend/` as React 18, JavaScript, Vite 5, and React Router 6. Retain Admin management, student/staff/academic setup, user and role administration, and finance/payroll/report screens. | Its current screens and contracts are already wired to the shared API. Rewriting its language or routing stack is outside the integration need and creates avoidable risk. |
| Teacher frontend | Keep `School-Teacher-Portal-main/School-Teacher-Portal-main/` as React 19, TypeScript, Vite 8, and React Router 7. Retain its Teacher dashboard, assigned classes/sections/subjects, scoped student views, assignments, attendance, published assessment views, and Teacher reports. | These are distinct Teacher workflows over the shared records; the active routes already call the Spring API. Do not replace them with Admin screens or revive the inactive JSON-server pages as a second system. |
| Frontend API adapters | Keep one small stack-native HTTP/auth adapter per SPA for now: Admin `src/api/client.js` and auth context; Teacher `src/services/apiClient.ts`, `teacherApi.ts`, and auth context. Keep their API envelope, token, error, and route expectations aligned with the common API contract. | Similar transport code is not duplicated domain logic. The SPAs have different languages, router/runtime generations, login routing needs, session keys, and expiry events. Consolidating them into a shared package is not justified until a real common packaging/runtime boundary is required. |
| Authentication and identity | Use the backend's one `AppUser`, `AuthService`, `AppUserDetailsService`, JWT, and persisted `LoginSession` implementation for both clients. Both use `/api/auth/login` and `/api/auth/logout`; Admin restores with `/api/auth/me`, while Teacher verifies access through `/api/teacher/profile`. | Login, credential checks, account state, session revocation, role/permission derivation, and user-to-staff linkage must not be independently implemented by either frontend. The client-side distinction after login selects the correct role experience; it does not authorize API access. |
| Authorization and Teacher scope | Keep server-side authorization in `SecurityConfig`, `PermissionInterceptor`/`PermissionService`, `AppUserDetailsService`, and `TeacherScopeResolver`. Every Teacher data operation derives scope from the authenticated principal, one eligible linked active TEACHING staff record, and validated active assignments. Deny Admin finance/user-management capabilities to Teacher accounts at the API. | Hiding navigation or trusting submitted staff, class, section, or student IDs is not security. Maintain permission checks and assignment-scoped data access in backend services/controllers even when the frontends also gate routes or menus. |
| API surface | Maintain one versioned-by-contract `/api` surface. Use common Admin management endpoints for authorized administration and dedicated `/api/teacher/...` read/write endpoints where Teacher policy requires constrained results or actions. Keep one response envelope and consistent authentication/error semantics. | Dedicated role-specific endpoints are appropriate when they enforce a distinct scope or capability; they must call shared services and entities, not fork the business rules. Do not point either active portal at `db.json`, JSON Server, or an independent API. |
| Services, entities, repositories | Keep one backend implementation for students, staff, assignments, classes, sections, subjects, timetable, attendance, assessments, finance, and reporting data. Share entities/repositories and domain services; add role-specific service facades only to enforce scope or shape responses, delegating domain decisions to shared logic. | Admin management and Teacher consumption are separate workflows, but they concern the same school data. Do not duplicate persistence models, eligibility rules, assignment validation, attendance validation, or assessment rules in a frontend or a second backend. |
| Database and migrations | Keep one MySQL database/schema and one Flyway migration history for production data. Continue using the project's isolated in-memory H2 setup for automated tests. New schema changes, if later approved, belong in additive Flyway migrations and are never applied to a live database as part of this phase. | This preserves common identity and domain records and prevents cross-portal data divergence. No schema change is currently approved or needed merely to document the architecture. |

## Consolidation versus intentional separation

**Keep separate by role:** Admin CRUD/configuration and finance/payroll screens; Teacher assignment-scoped roster/profile and timetable views; Teacher attendance workflow; Admin user/staff/assignment management; Teacher-only academic/attendance summaries versus Admin financial reports. Separate layouts, navigation, forms, and presentation DTOs are acceptable when they serve these distinct tasks.

**Keep common:** Authentication and persisted sessions; account, staff-link, and role/permission identity; teacher-assignment validation and authorization scope; student, class, section, subject, timetable, attendance, assessment, finance, and reporting business rules and persisted records; API security and error semantics.

**Do not consolidate without new evidence:** The two thin HTTP adapters and auth contexts. They have overlapping mechanics but are implemented in JavaScript and TypeScript applications with different toolchain versions and session handling. Their current overlap does not justify a new shared package, a frontend stack migration, or a rewrite. If repeated contract drift appears, first add cross-portal contract tests or a small shared API schema; do not move domain rules into either client.

**Inactive Teacher mock code:** `src/services/mockData.ts`, `db.json`, and legacy JSON-server-oriented components are not part of active `App.tsx` routes. Leave these existing files untouched in this phase. If a legacy screen is ever reactivated, migrate its data access to the common API and confirm its role scope before enabling it.

## Approved scope and impact analysis

**Approved scope (2026-10-16):**

- Admin can create and edit assessments, publish them, and unpublish them.
- The platform needs a weekly timetable organized by class and section, with subject, teacher, room, and period on each entry.
- Teachers enter marks only for assessments/classes authorized by their active teaching assignments. Admin reviews and publishes results. Published results are visible only to authorized users.

These decisions supersede the earlier "further requirements needed" classification for the capabilities explicitly listed above. The detailed rules below are impact analysis and recommendations, not additional approved product rules. Do not implement open questions as assumptions.

### Assessment authoring

**Existing implementation:** `backend/src/main/java/com/schoolenterprise/assessment/` contains `Assessment`, `AssessmentRequest`, `AssessmentResponse`, `AssessmentRepository`, `AssessmentService`, and `AdminAssessmentController`. `POST /api/admin/assessments` creates an assessment with title, class, optional section, subject, academic year, date, maximum marks, and initial `DRAFT` or `PUBLISHED` status. The service enforces Admin role, same-school class/subject/year, active year/subject/optional section, matching section class/year, subject-class-year mapping, date within academic year, positive maximum marks, and an audit event. `TeacherAssessmentController` exposes only `GET /api/teacher/assessments[/{id}]` for published assessments in a teacher's active assignment scope. The Teacher frontend routes those reads; the Admin frontend has no assessment route or screen. Legacy Teacher exam/marks components use `mockData.ts`/`db.json` and are not active routes; they are not a safe implementation to reuse.

**Missing:** Admin assessment list/detail/edit and explicit publish/unpublish operations. Creating directly as `PUBLISHED` currently skips a later publish review. There is no state-transition rule for edits after publication or after marks exist.

**Proposed Admin workflow/API:** Add a role-gated Admin assessments list/detail screen with filters for academic year, class, section, and status; create and edit forms; and explicit publish/unpublish actions. Reuse `POST /api/admin/assessments`; add `GET /api/admin/assessments[?academicYearId=&classId=&sectionId=&status=]`, `GET /api/admin/assessments/{id}`, `PUT /api/admin/assessments/{id}`, and a status transition such as `PATCH /api/admin/assessments/{id}/status` accepting only approved transitions between `DRAFT` and `PUBLISHED`. Continue serving Teacher read views from the shared assessment service and expose only published assessments.

**Authorization:** Existing creation checks `PermissionService.isAdmin()` in the service; the controller does not declare a permission annotation. Preserve Admin-only authoring and apply the same authorization to list/detail/edit/status endpoints. If the project later wants non-ADMIN school leadership to author assessments, that is a separate role decision and requires explicit permission design. Teacher access is read-only today; do not give teachers assessment metadata authoring rights.

**Validation and edge cases:** Reuse the current class/section/subject/year consistency checks and maximum-mark validation on edit, not only create. Define whether an assessment may be edited while published; recommended safe behavior is to require unpublishing before changing metadata that Teachers rely on. Define behavior if marks exist (freeze class/subject/year/section/max marks, or require an explicit reviewed correction process). Define duplicate assessment policy; there is currently no uniqueness rule, and title/date alone may not identify duplicates. Ensure status transitions and audit actor/action are recorded. Creation currently permits immediate `PUBLISHED`; decide whether that remains allowed once explicit review/publish exists.

**Schema:** Existing `V19__assessments.sql` already persists the assessment fields and DRAFT/PUBLISHED status, with FKs and scope indexes. Basic edit and status changes need no new column, but likely require additive indexes only if list performance requires them. The entity has no `created_by` ownership field; create actions are recorded through `AuditService`. The approved role policy is Admin-wide rather than creator-only, so creator ownership should not be added unless audit/history requirements demand it.

### Weekly timetable

**Existing implementation:** `TimetableEntry` and `V15__timetable_management.sql` persist school, class, section, academic year, day, period number/name, optional string start/end times, subject, staff, optional room, and status. `/api/timetable` already supports optional section/class/year/staff filters and GET detail, POST create, PUT update, and DELETE. `AcademicsService.saveTimetableEntry` validates class/section/year consistency, active subject/staff, subject mapping, and an active teacher assignment. It detects active-entry clashes for the same section slot, teacher slot across the school/year, and nonblank room slot across the school/year. `TimetableEntryRequest` constrains period number to 1–12. `School-Teacher-Portal-main/.../Dashboard.tsx` reads and displays the teacher's assignment-filtered schedule; `frontend/src/pages/TeacherProfilePage.jsx` displays an individual staff timetable. Neither portal has a class/section weekly timetable authoring screen. The current controller excludes teacher roles and applies `classes` view/create/edit/delete permissions to the respective endpoints.

**Missing:** Admin weekly grid/editor and an explicit canonical definition for weekdays/periods. Day is only uppercased, not restricted to a weekday; start/end times are strings with no format, ordering, or overlap checks; requested status is not constrained to ACTIVE/INACTIVE. Conflict checks are application-side and are not atomic with saving, and the migration has no slot uniqueness/check constraints. Room is optional and is not checked against a room inventory or the class's classroom count. There are no timetable-specific service/controller tests.

**Proposed Admin workflow/API:** Add a class/section weekly grid in the Admin React/JavaScript portal. Select academic year, class, and section; display entries in configured weekday/period order; create/edit/delete one period entry with subject, teacher, room, and period. Reuse `GET /api/timetable?classId=&sectionId=&academicYearId=`, `POST /api/timetable`, `PUT /api/timetable/{id}`, `DELETE /api/timetable/{id}`, and existing class/section/subject/staff/year selectors. A new bulk endpoint is not required by the approved scope. Keep teacher schedule reads assignment-scoped and read-only.

**Authorization:** Keep timetable writes behind existing `classes:create|edit|delete` permissions and the current exclusion of Teacher roles. Require school-scope validation on every selected class, section, subject, academic year, staff record, and assignment; never trust IDs supplied by the UI as proof of assignment.

**Validation and conflict handling:** Preserve the current section-slot, teacher-slot, and room-slot checks and add tests. Sort by a canonical weekday rank and period number, not alphabetically on weekday labels. Validate weekday, allowed status, time syntax, and `start < end`; detect overlapping clock intervals if arbitrary period times are allowed. Normalize room identity/case consistently. Exclude the entry being edited from collision checks. Decide what inactive entries do before changing the existing "only ACTIVE entries conflict" behavior. Treat same-class/different-section same-slot collisions separately: parallel section lessons may be legitimate, so do not forbid them without a school rule. Application checks need transaction/concurrency protection or a database-safe uniqueness design to prevent two simultaneous writes from occupying the same resource slot.

**Schema:** Existing entry columns can support the approved dimensions; no new schema is required for a basic weekly UI over the current CRUD API. A migration may be needed if approved period definitions must be centrally configured, if `start_time`/`end_time` are normalized to SQL TIME or linked to a period entity, or if active-slot concurrency constraints require database-enforced slot keys/constraints. `room` currently has no room entity/FK. Do not create a period/room inventory schema until the open policy questions are answered.

**Open timetable rules:** Which weekdays constitute a school week and what display order/locale applies? Are periods numbered 1–12 for all school days/years, or does each academic year have its own period schedule? Are period start/end times required, and can periods vary by day? Is room mandatory, free text, or selected from a school room inventory? Should a same-class entry across different sections conflict, or can sections run concurrently? Do inactive entries reserve slots? Are overlapping clock intervals possible across different period numbers? Should timetable changes be audited only, or require publication/approval before Teachers see them? The last item is not implied by "weekly timetable" and remains unapproved.

### Marks and results

**Existing implementation:** There is no assessment-mark or assessment-result entity, repository, API, service, or migration. `Assessment` contains `maxMarks` and schedule status only. Teacher assessment access provides published metadata; the active Teacher assessment detail is read-only. Legacy `Exams.tsx`/`ExamDetails.tsx` and `services/mockData.ts` contain demo/mock marks flows but are not routed by active `App.tsx` and have no shared-backend authorization contract. `Enrollment` and teacher `TeacherScopeResolver` provide reusable academic-year section membership and active class/section/subject/year assignment data. Assessment creation and teacher reads are tested in `AssessmentServiceTest`; no marks/result tests exist.

**Proposed UI workflow/API:** In the Teacher Portal, show a marks-entry roster from an assigned assessment, allow entry/update of one mark per eligible student, and submit a batch. In the Admin Portal, show submitted marks by assessment/cohort, review them, and publish results; expose only released results to eligible views. Candidate APIs are `GET /api/teacher/assessments/{id}/marks`, `PUT /api/teacher/assessments/{id}/marks` (batch upsert), `GET /api/admin/assessments/{id}/results`, `POST /api/admin/assessments/{id}/results/publish`, and `GET /api/teacher/assessments/{id}/results` for published results within teacher scope. Final names/verbs and whether a teacher saves partial batches or submits a completed roster should follow the approved product workflow. Do not reuse mock JSON-server endpoints.

**Authorization and assessment ownership:** Mark entry must derive the actor's linked staff ID from the authenticated principal; ignore or reject client-supplied teacher/staff ownership. Re-load the persisted assessment and current `TeacherScope` on every read/write. Require the active assignment to match assessment class and academic year; require subject match for subject-specific assignments; require section match for section-specific assessments. For an assessment with no section, require assignment coverage of that class/year/subject and constrain each student to an eligible enrollment in the assessed class/year. The current `AssessmentService.allowed` predicate supports published assessment reads and permits a class-level assessment for an assignment whose section/subject are null as a wildcard; confirm whether a class-teacher assignment with no subject is authorized to enter marks for every subject before reusing that behavior. Return not-found or forbidden consistently for out-of-scope IDs to avoid data disclosure.

The assessment currently has no creator/owner field. Approved requirements authorize Admin review/publication and teacher entry by assignment, not creator-only ownership. Track mark provenance (`entered_by_user_id` and/or linked `staff_id`, timestamps, and audit history); do not let a caller claim another teacher as the owner. If product means a narrower assessment owner (for example, only its creating Admin can edit), confirm that separately.

**Validation, result state, and visibility:** Require each score to be numeric, nonnegative, at most that assessment's `maxMarks`, and within the agreed scale/precision; reject NaN/infinity at the API boundary. Validate the student is active/eligible and enrolled in the target section or class for the assessment's academic year. Prefer `Enrollment` for historical year membership over `Student.currentSectionId`, which can change. Enforce one mark per assessment/student with a DB uniqueness constraint and idempotent upsert behavior; reject duplicate student IDs within a batch and report row-level errors without partial success unless transactions guarantee all-or-nothing. Distinguish assessment schedule `status` (DRAFT/PUBLISHED) from results review/publication state. Admin publication must be an explicit server-side state transition, audited with actor/time; teachers must not see unpublished scores/results. Re-check authorization on every results query and return no data for out-of-scope cohorts.

Initially, the least-privilege authorized viewers are Admin reviewers/publishers and Teachers with a current matching assignment. Student/guardian result access is not supported by either current portal and remains an open product/access requirement; do not expose results to them until identity, portal, consent/privacy, and scope rules are specified.

**Authorization impact:** Current `PermissionService.require` makes Teacher roles read-only, and `AppUserDetailsService` strips their permissions except an explicit set of read permissions. Teacher marks are an intentional narrow write exception, not permission to change that general rule. Before implementation, choose a dedicated backend authorization action/check for mark entry that combines Teacher role with live assessment assignment scope; do not simply grant broad `assessments:edit` or bypass assignment checks. Admin review/publication must be restricted to Admin. Use the existing audit service for score changes and result release.

**Schema:** An additive Flyway migration is required for persisted marks/results. Candidate schema: `assessment_mark` with FK to assessment and student, decimal score, entered-by user/staff provenance, timestamps/audit metadata, and unique `(assessment_id, student_id)`; add a separate result-publication/review state (either a carefully modeled assessment-result status with reviewer/publisher metadata or a one-per-assessment release table). Do not conflate schedule status with result release. Confirm whether review is whole-assessment or section-by-section, whether marks can be revised after publication, whether missing/absent/exempt marks are represented by null/status rows, and whether partial publication is possible before finalizing the schema.

**Tests:** Extend `AssessmentServiceTest` for Admin edit/state transitions and rules once specified. Add service/controller tests for teacher assignment matching across class/section/subject/year; active student/enrollment matching including historical academic years; out-of-scope denial; score boundaries/precision; duplicate student batch rows; idempotent updates; partial vs atomic failure semantics; Admin-only review/publication; audit provenance; hidden results before publication; and only authorized results after publication. Add repository/integration tests for the uniqueness constraint and migration compatibility. Add frontend tests if existing test setup can cover each portal; the Teacher portal currently has no test script.

## Open questions before feature implementation

1. For assessment editing, may a published assessment be edited directly, or must it be unpublished first? Can a published assessment with marks change its maximum marks or cohort?
2. Is assessment metadata ownership Admin-wide (recommended based on the approved "Admin" role) or restricted to the Admin who created it? Is direct creation in PUBLISHED status allowed?
3. Does an assigned class teacher without a subject-specific assignment enter marks for every assessment subject in that class, or only assessments where a matching subject assignment exists?
4. For a class-level assessment (`sectionId == null`), which sections/students are included, and how should transfers, inactive enrollment, absences, exemptions, and withdrawn students be represented?
5. Are marks decimal, integer, or configurable precision? May teachers submit partial rosters and edit after submission? What is the review/revision process after result publication?
6. Which identities may view published results? Admin and currently assigned teachers are recommended initial scope; student/guardian access needs separate authorization and privacy requirements.
7. For timetable, what are the canonical weekdays, period/time definitions, room inventory/requirement, same-class multi-section policy, inactive-entry semantics, and schedule publication behavior?
8. The Stage 1 source document `School_Enterprise_Stage_1_Core_Administration_and_Finance.docx` is referenced as an external desktop/download copy and is not present in the repository. The root `PROJECT_CONTEXT.md` states that attendance, timetable, exams, and later stages were originally out of Stage 1 scope; this approved integration scope should therefore be treated as additional platform scope, not a change to the historical Stage 1 acceptance spec.

## Recommended implementation sequence after approval

1. Resolve the open policy decisions above that change permissions, result visibility, timetable conflicts, or schema. Record them as API-level acceptance criteria before coding.
2. Implement timetable rule/validation tests and backend hardening only for agreed weekday, period/time, room, status, and concurrency policies; reuse `TimetableEntry` and existing CRUD endpoints where adequate. Then add the Admin class/section weekly grid using those contracts.
3. Complete assessment Admin list/detail/edit and explicit publish/unpublish state transitions in the shared backend; add service/API tests, then connect the Admin authoring UI. Keep existing Teacher published-only assessment reads.
4. Design and add the additive marks/result Flyway schema after resolving cohort, partial-entry, precision, revision, and publication semantics. Do not apply the migration to a live database without explicit approval.
5. Implement scoped Teacher mark-entry and Admin review/publish/result APIs with row/role/scope checks, audit, and service/integration tests before connecting Teacher marks UI and Admin review UI.
6. Verify both portals against the same local backend: frontend builds/tests, authorization boundaries, timetable conflicts, assessment state transitions, mark validation, result publication, and visibility for in-scope and out-of-scope users.

Timetable work can proceed independently of marks/results once its policy questions are answered. Marks/results depend on assessment identity/cohort semantics and approved mark/publication rules; implement the shared backend contract and migration before either marks UI.

## Phase 3 timetable policies and implementation plan

This section records the approved timetable policies and a file-by-file plan. It supplements and supersedes the earlier timetable-specific open questions above where they conflict. It is analysis only; no source change, migration, or database operation is authorized here.

### Approved policies and remaining decisions

- Working days must be configurable. There is no existing working-day setting discovered in the School entity, school APIs, timetable schema, or migration history. The Admin teacher-profile timetable currently hardcodes all seven weekday names/order in `frontend/src/pages/TeacherProfilePage.jsx`; the Teacher dashboard displays the weekday string returned by the API.
- Room remains optional. A missing/blank room must not block timetable create/update and must not generate a room collision.
- Distinct sections of one class may occupy the same day/period concurrently. A collision is rejected only if the same section, teacher, or nonblank room is already occupied under current active-entry semantics.
- Timetable writes take effect immediately. There is no separate publish/approval state or publish API; a subsequent authorized read after a successful save sees the saved entry.
- Preserve the existing Admin staff-profile timetable and Teacher assigned-timetable experiences. Add a separate Admin weekly class/section grid; do not replace either portal.

**Open configuration question:** Is the configured working-day list school-wide or specific to an academic year, and who is authorized to change it? Recommended first design is a school-level, Admin-managed ordered list using the existing timetable/academic permissions, with no implicit weekday defaults. Confirm that scope before choosing storage or endpoint permissions. Also confirm whether users already holding `classes:edit` are intended to manage this school-wide setting. No Monday–Friday or Monday–Saturday default is assumed.

**Other open timetable rules:** The request DTO already restricts period numbers to 1–12; this plan preserves that range and sorts ascending unless a product decision changes it. Period definitions/counts and times are not currently configurable. Current conflicts compare day plus period number, not overlapping clock intervals; decide whether periods with different numbers but overlapping start/end times should also conflict. The approved immediate-effective policy means no publish state, but does not itself require existing open Teacher pages to update via push while they remain open; the current read-on-load behavior is retained unless live refresh is explicitly required.

### Backend validation and conflict plan

1. **Configured weekday:** Normalize the submitted ISO weekday code to uppercase, reject blank/unrecognized values, and require membership in the persisted/configured working-day set for the applicable school (and academic year only if that scope is approved). Do not accept arbitrary text, invent a weekday default, or hardcode a Monday–Friday/Saturday schedule. Return the configured list/order to authorized Admin UI consumers. Persist and return a stable ISO weekday code; use configuration order for presentation.
2. **Period value/order:** Preserve request `@Min(1)`/`@Max(12)` and integer semantics unless product owners change the existing bound. Sort days by configured order and entries by integer period ascending; do not sort period labels lexically. Reject null/out-of-range periods before repository calls. The existing schema supports period number/name/time fields and needs no period migration for this scope.
3. **Eligibility:** Continue requiring matching active class, section, academic year, subject mapping, active teacher, and active teacher assignment. Keep lookups school-scoped. For edits, exclude the current entry by ID from all collision checks; for delete/update, first confirm the entry belongs to the current school.
4. **Section/class collision:** Reject an active entry already occupying the same section + year + configured day + period. Do not reject another section of the same class at the same slot. Preserve the distinction between section occupancy and class identity.
5. **Teacher collision:** Reject an active timetable entry for the same teacher/staff ID + year + day + period anywhere in the school. Use the same configured weekday normalization and active-entry rule as section checks.
6. **Room collision:** If the room is null/blank, skip room checks and persist null as today. If nonblank, normalize whitespace and compare consistently (currently case-insensitive) against active entries for the same room + year + day + period anywhere in the school. Room conflicts remain independent of class/section; different sections may run concurrently only when there is no shared teacher or room.
7. **Status/time:** Reject unsupported status values rather than persisting arbitrary strings; preserve current behavior that only `ACTIVE` entries occupy slots unless owners explicitly change it. Keep room optional. Validate start/end as valid times and require `start < end` if one or both are entered, but first confirm whether the pair is optional together. Do not add cross-period time-overlap conflicts until owners decide how configured periods/times interact.
8. **Concurrency:** Existing conflict checks are service-side and can race under simultaneous saves. Before guaranteeing collision-free concurrent writes, select a transactional strategy (for example, serialize timetable mutations per school/year or add database uniqueness keys for section, teacher, and nonblank room slots). Check historical duplicate data and MySQL/H2 compatibility before any index migration. This plan does not presume a safe uniqueness migration is already possible.
9. **Immediate effect:** A successful POST/PUT becomes the current row immediately; there is no schedule publication state. A subsequent Admin or scoped Teacher GET returns the active saved entry. Existing soft-inactive entries remain excluded from Teacher timetable display.

### Database impact

`V15__timetable_management.sql` already represents every approved entry field, including nullable room, and supports the current entry endpoints. Do not alter or recreate it. A weekly grid alone requires no entry-schema change.

There is currently no persistent/configurable working-day data in `School`, `TimetableEntry`, or a related migration. If the configuration is Admin-editable and must survive restarts, an additive migration is likely necessary. Recommended normalized shape is a `school_working_day` table with school FK, ISO weekday code, and explicit display order; unique constraints should prevent duplicate weekday codes and duplicate order per school. The table should have no Monday–Friday default rows: initial setup must explicitly choose the working-day set. If policy is academic-year-specific, the key and FK must instead include academic year. A deployment-property configuration would avoid a schema migration but would not give an Admin UI durable self-service configuration; this is why scope/ownership must be confirmed. No migration is created or run in this planning task.

Optional database collision constraints are a separate decision from the working-day migration. MySQL unique keys do not express "only ACTIVE rows" as a portable partial constraint in the current schema. If choosing generated active-slot keys or serialized service writes, first test existing data, foreign keys, and H2/MySQL behavior. Preserve the ability for distinct sections of one class to share a period by including section ID in the section slot key, not class ID.
