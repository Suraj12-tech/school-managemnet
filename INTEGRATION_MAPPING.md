# School Enterprise Portal Integration Mapping

## Scope and architecture

The platform uses one Spring Boot API and one shared relational data model. The Administrator and Teacher portals are separate React applications with role-specific screens; neither owns school-data business rules. The backend remains authoritative for authentication, permissions, assignment validation, and teacher data scope.

## Frontend stack and client comparison

| Portal | Existing stack | API/session implementation | Local backend connection |
|---|---|---|---|
| Administrator | React 18, JavaScript, Vite 5, React Router 6. Build is `vite build`; tests are the Node test runner. | `frontend/src/api/client.js` handles the envelope, bearer token, errors, and session-expiry event. `AuthContext.jsx` stores the Admin session in localStorage and restores it with `/api/auth/me`. | Vite proxies `/api`, `/v3`, and Swagger paths to `http://localhost:8080`; `VITE_API_URL` can override the origin. |
| Teacher | React 19, TypeScript, Vite 8, React Router 7 with hash routing. Build runs `tsc -b` followed by Vite. No test script is defined. | Typed `teacherApi` uses `apiClient.ts`, a separate localStorage token key, and a Teacher-profile request to validate the session. | Vite proxies `/api` to `http://localhost:8080`; `VITE_API_URL` can override the origin. |

The API wrappers overlap in transport responsibilities, but they are separate thin adapters in different language/toolchain stacks and currently use distinct session keys and expiry events. Consolidating them would require a shared package/build contract or a stack change without removing backend business logic duplication. The chosen boundary is therefore one shared backend for auth, identity, authorization, and domain rules, with each frontend retaining its minimal stack-native adapter.

## Audit gaps and verification

- The Teacher README previously described the portal as read-only and said attendance and reports were not routed, contrary to the active routes. It now documents the implemented role experience.
- The Admin login HTTP 403 issue was not reproducible in this audit: the acceptance flow authenticates the seeded Admin and successfully reads Admin dashboard, users, and roles. No security bypass or permission grant was made.
- Admin assessment UI and assessment marks/results are not implemented by the current Admin frontend/API. Teacher assessment reads are limited to published assessments. These remain explicit capability gaps rather than being represented as complete.
- Current tests/builds use local dependencies and an in-memory H2 test database. No live database was touched and no migration was applied to a live database.
- Backend acceptance tests exercise Admin/Teacher login, unauthorized access, role separation, assigned-class/section/student reads, and finance denial. Frontend builds verify each app's compilation; no browser-driven end-to-end test runner is configured.
